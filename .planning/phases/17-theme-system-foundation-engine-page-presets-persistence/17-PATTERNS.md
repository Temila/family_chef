#### `frontend/index.html` (MODIFY, config, FOUC bootstrap)

**Purpose:** Extend the existing inline FOUC script to read `fc_active_theme` and inject `<style id="fc-dynamic-theme">` before first paint.

**Closest analog:** `frontend/index.html:8-16` (existing inline script — do NOT replace).

**Pattern to mirror (existing — extend, don't replace):**
```html
<script>
  (function(){
    var saved = localStorage.getItem('fc_theme');
    var preferDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
    if (saved === 'dark' || (!saved && preferDark)) {
      document.documentElement.setAttribute('data-theme', 'dark');
    }
  })();
</script>
```

**Differences from analog:**
- Add a second block (AFTER the existing data-theme block) that reads `fc_active_theme`, JSON-parses it, calls a synchronous `buildThemeCssSync(sourceColors, variant)` export from `theme-engine.js`, and appends `<style id="fc-dynamic-theme">` to `document.head`.
- The new block must be wrapped in `try/catch` — malformed JSON → silently fall back to `tokens.css` defaults (per D-10).
- Because the inline script runs before Vite hydration, the engine module must be importable synchronously as ESM. Vite bundles it into the main entry chunk.

**Acceptance-relevant identifiers:**
- localStorage keys: `fc_theme` (existing — light/dark) and `fc_active_theme` (new — JSON `{ sourceColors: {primary, secondary, tertiary}, variant }`).
- Style element id: `fc-dynamic-theme` (D-08).

#### `frontend/src/theme/theme-engine.js` (NEW, engine, pure module + DOM helper)

**Purpose:** Pure module that derives light + dark MD3 schemes from seed colors, builds CSS text blocks, and idempotently injects a `<style id="fc-dynamic-theme">` element. Called by both the inline FOUC bootstrap AND `ThemeContext` (must produce byte-identical CSS in both paths).

**Closest analog:** `scripts/generate-tokens.cjs:141-320` (`main()` function — build-time MCU usage).

**Pattern to mirror (MCU import + scheme property read + hex conversion):**
```javascript
// scripts/generate-tokens.cjs:153-166
const mcu = await import(pathToFileURL(path.join(mcuPackageRoot, 'index.js')).href);
const { argbFromHex, themeFromSourceColor } = mcu;

const primaryArgb = argbFromHex(PRIMARY_HEX);
const secondaryArgb = argbFromHex(SECONDARY_HEX);
const tertiaryArgb = argbFromHex(TERTIARY_HEX);

const theme = themeFromSourceColor(primaryArgb, [
  { name: 'secondary', value: secondaryArgb, blend: true },
  { name: 'tertiary', value: tertiaryArgb, blend: true },
]);

const lightScheme = theme.schemes.light;
const darkScheme = theme.schemes.dark;
```

**Differences from analog:**
- The build script writes a single `:root` + `[data-theme="dark"]` block to disk; the engine module must instead RETURN the same shape as a string, then have a separate `injectThemeCss(cssText)` helper append/replace the live `<style>` element.
- Two exported entry points (per UI-SPEC §6 Path A vs Path B): `buildCssSync(sourceColors, variant)` for the inline FOUC bootstrap (synchronous, no React); `injectThemeCss(cssText)` for ThemeContext (DOM side-effect).
- One critical new step the build script does NOT do: emit the **dark-mode `--md-elevation-*` overrides** in the `[data-theme="dark"]` block, using `color-mix(in srgb, var(--md-color-surface-tint) N%, transparent)` (per UI-SPEC § Color → Elevation in Dark Mode and PITFALLS.md Pitfall 4). Light mode leaves elevation untouched.
- Hex conversion: `scripts/generate-tokens.cjs:87-92` `hexFromArgb` — copy verbatim.
- camelCase→kebab: `scripts/generate-tokens.cjs:94-97` `toKebab` — copy verbatim.
- The `DIRECT_ROLES` array (`generate-tokens.cjs:102-112`) is the canonical list of `--md-color-*` semantic roles the engine must emit. Copy it.
- The `SURFACE_PALETTE_ROLES` (`:116-125`) and `SPECIAL_PALETTE_ROLES` (`:128-131`) are the surface container levels + surfaceTint + surfaceVariant. Engine reads them from the `theme.palettes.neutral.tone(...)` family the same way.
- For TonalSpot variant, `DynamicScheme` is the recommended path (per `scheme.d.ts:18-22` "DEPRECATED. The `Scheme` class is deprecated in favor of `DynamicScheme`"). However, `themeFromSourceColor` returns a `Theme` with `schemes: { light: Scheme, dark: Scheme }` (`theme_utils.d.ts:48-63`) — the engine can read `.primary`/`.onPrimary`/etc. properties from those `Scheme` instances (the shape matches `DIRECT_ROLES`).

**Acceptance-relevant identifiers:**
- Exports: `buildCssSync(sourceColors, variant)`, `buildCss(sourceColors, variant)`, `injectThemeCss(cssText)`, `lightTokenNames` (constant — for test/audit).
- Selector: `:root { ... }` and `[data-theme="dark"] { ... }`.
- The synthesized `<style>` always has `id="fc-dynamic-theme"`.

**Hex-lint escape:** This file MUST emit hex strings (it is the only legitimate emitter besides `presets.js`). The new `scripts/check-tokens.sh` Check #8 must scope to `frontend/src/{components,pages}/**/*.jsx` and EXEMPT `frontend/src/theme/presets.js` AND `frontend/src/theme/theme-engine.js` (or scope to `**/*.jsx` glob which already excludes `.js` files — recommend the `.jsx` scope so engine is naturally exempt).

#### `frontend/src/theme/theme-context.jsx` (NEW, context, Provider + hook with memoized value)

**Purpose:** React Provider + `useTheme()` hook. Exposes `{ activeTheme, setActiveTheme, customThemes, refreshCustomThemes }`. On mount + on `activeTheme` change, calls `theme-engine.injectThemeCss(buildCssSync(...))` and persists to localStorage. On mount, fire-and-forget `GET /api/themes` for sync.

**Closest analog:** `frontend/src/contexts/CategoriesContext.jsx:1-78` (Provider + `useXxx` shape).

**Pattern to mirror (Provider + custom hook + `useEffect` mount):**
```jsx
// frontend/src/contexts/CategoriesContext.jsx:16-68
export const CategoriesProvider = ({ children }) => {
  const [allCategories, setAllCategories] = useState([]);
  const [loading, setLoading] = useState(true);

  const loadCategories = useCallback(async () => {
    try {
      const res = await api.getCategories();
      setAllCategories(res.items || []);
    } catch (err) {
      console.error('Failed to load categories:', err);
    } finally {
      setLoading(false);
    }
  }, []);

  useEffect(() => {
    queueMicrotask(() => { loadCategories(); });
  }, [loadCategories]);

  const value = {
    allCategories,
    loading,
    getByType,
    getTypeMeta,
    categoryTypes,
    reload: loadCategories,
  };

  return (
    <CategoriesContext.Provider value={value}>
      {children}
    </CategoriesContext.Provider>
  );
};

export const useCategories = () => {
  const context = useContext(CategoriesContext);
  if (!context) {
    throw new Error('useCategories must be used within a CategoriesProvider');
  }
  return context;
};
```

**Differences from analog — TWO LOAD-BEARING ONES:**
1. **DIVERGES (memoize):** `CategoriesContext` constructs `value` as a fresh object each render → consumers re-render whenever any provider state changes. Phase 17 ThemeContext MUST wrap the value in `useMemo(() => ({...}), [deps])` (per CONTEXT D-11 + RESEARCH Pitfall 7). Otherwise Phase 18 drag-time updates re-render the whole app.
2. **DIVERGES (apply side-effect):** ThemeContext must also call `theme-engine.injectThemeCss(buildCssSync(activeTheme.sourceColors, activeTheme.variant))` inside a `useEffect` keyed on `activeTheme` (mount + change). CategoriesContext has no DOM-touching side effect.
3. **Auth-aware fetch:** `refreshCustomThemes` should be called from an effect that uses `useAuth().user?.id` as the trigger (only fetch after login). CategoriesContext always fetches on mount.

**Pattern to mirror (mount effect with `queueMicrotask` to dodge set-state-in-effect):**
```jsx
useEffect(() => {
  queueMicrotask(() => { loadCategories(); });
}, [loadCategories]);
// UserWishesPage.jsx:51-78, 110-124 use the same pattern (or inline .then() chain — see UserWishesPage.jsx:110-124 for the more defensive variant)
```

**Acceptance-relevant identifiers:**
- Exports: `ThemeProvider`, `useTheme` (default export `ThemeContext`).
- `useTheme()` return shape: `{ activeTheme, setActiveTheme, customThemes, refreshCustomThemes, applyTheme, resetToDefault }`.
- localStorage write: `localStorage.setItem('fc_active_theme', JSON.stringify({ sourceColors, variant }))`.
- localStorage read on mount: `localStorage.getItem('fc_active_theme')` → JSON.parse → validate shape → use; else fall back to `PRESETS[0]` (default).

#### `frontend/src/components/theme/ThemeCard.jsx` (NEW, component, card-as-preview)

**Purpose:** Renders a single theme card. The outer card is themed with the page's active theme tokens; the inner preview wrapper is themed with THIS card's tokens via scoped `<style>` injection. Card click → `setActiveTheme(thisTheme)`.

**Closest analog:** `frontend/src/components/DishCard.jsx` (existing composite card) — read the structure to understand slot-based composition with `<Card>` primitive.

**Pattern to mirror (Card primitive usage with clickable variant + ripple):**
```jsx
// frontend/src/components/primitives/Card.jsx:17-65
const Card = forwardRef(function Card({
  variant = 'elevated',
  image, header, footer, onClick, className = '', children, ...rest
}, ref) {
  const isClickable = Boolean(onClick);
  const classes = [
    'md-card',
    `md-card--${variant}`,
    isClickable && 'md-card--clickable',
    className,
  ].filter(Boolean).join(' ');
  ...
  return (
    <Ripple disabled={!isClickable}>
      <div ref={ref} className={classes} onClick={onClick} role={isClickable ? 'button' : undefined} tabIndex={isClickable ? 0 : undefined} onKeyDown={handleKeyDown} {...rest}>
        {image && <div className="md-card__image">{image}</div>}
        {header && <div className="md-card__header">{header}</div>}
        <div className="md-card__body">{children}</div>
        {footer && <div className="md-card__footer">{footer}</div>}
      </div>
    </Ripple>
  );
});
```

**Differences from analog — THE LOAD-BEARING DIFFERENCE:**
- ThemeCard wraps a `<div data-fc-theme-scope={themeId}>` inside `<Card>`. ## 4. Style Notes Specific to This Phase

### Where Phase 17 DIVERGES from existing patterns

1. **Memoized Context (DIVERGES from `CategoriesContext`/`AuthContext`):**
   - `frontend/src/contexts/AuthContext.jsx:47-57` constructs `value` as a fresh object literal each render. `CategoriesContext.jsx:54-61` does the same. Neither uses `useMemo`.
   - **ThemeContext MUST wrap `value` in `useMemo` with the appropriate dep array.** Otherwise, every provider re-render re-creates the value, causing every consumer to re-render — which becomes a perf disaster in Phase 18 when drag-time state updates fire 60×/sec.
   - Verified existing usage of `useMemo` in the codebase: `frontend/src/pages/AdminDishesPage.jsx:27`, `OrderPage.jsx:30`, `ChefDishesPage.jsx:27` — pattern is `useMemo(() => ..., [deps])`.

2. **Apply layer via `<style>` element (NEW pattern, no existing analog):**
   - There is NO existing precedent in this codebase for synthesizing a `<style>` element at runtime. `ToastContext.jsx:320` uses `<style>{SNACKBAR_STYLES}</style>` JSX, but that is a STATIC string — not built at apply-time.
   - `theme-engine.js`'s `injectThemeCss` is a brand-new pattern. It must NOT import React or any JSX (Phase 17 must call it from the inline FOUC bootstrap before Vite hydration).

3. **Card-as-preview via CSS-var scoping (NEW pattern, no existing analog):**
   - `frontend/src/components/primitives/Card.jsx` and friends natively read `--md-color-*` from CSS — that's the load-bearing property. But no existing component wraps a subtree in a `<div data-fc-theme-scope>` and overrides CSS vars via a scoped `<style>` selector. Phase 17 introduces this for the first time.

4. **Dark-mode elevation override (DIVERGES from `tokens.css:163-167`):**
   - `frontend/src/css/tokens.css:163-167` hardcodes `rgba(0,0,0,X)` for `--md-elevation-1..5`.
   - **Phase 17 emits a `[data-theme="dark"]` block with 5 elevation overrides** that use `color-mix(in srgb, var(--md-color-surface-tint) N%, transparent)` (per UI-SPEC § Color → Elevation in Dark Mode + PITFALLS.md Pitfall 4).
   - This is a deliberate, in-engine override of an MD3 hardcoded default. Light mode leaves elevation untouched.
   - The new check is: if `var(--md-color-surface-tint)` is overridden (i.e., a custom theme is active in dark mode), the elevation must also be overridden to use the custom tint at low alpha. The engine module handles this conditionally.

5. **MCU in production bundle (DIVERGES from devDep-only):**
   - `frontend/package.json:28` has MCU as `devDependency` (only used by the build-time `scripts/generate-tokens.cjs`).
   - **Phase 17 promotes MCU to `dependencies`** so Vite bundles it into the browser runtime. No other package has ever been promoted this way. This is the single npm-only change of Phase 17.

6. **Per-card scoped `<style>` lifetime (NEW consideration):**
   - When rendering N cards (5 presets + N custom), each `ThemeCard` mounts its own scoped `<style>` element. The React reconciliation key is `theme.id`. If `theme.sourceColors` change (Phase 18 editor), the key stays the same but the `<style>` content changes — handled by re-rendering the inner content via `useMemo` keyed on `JSON.stringify(theme.sourceColors) + theme.variant`. Phase 17 doesn't need this care (presets are static, custom are loaded once), but the architecture supports Phase 18.

7. **Per-user soft-isolation via API endpoint enumeration (DIVERGES from `Favorite`'s enumeration resistance):**
   - `favorites.py` does NOT include user_id in route paths — the endpoint enumerates "the current user's" favorites by `where(Favorite.user_id == current_user.id)`.
   - **Same pattern for themes**: `GET /themes` returns current user's themes only; `PUT /themes/{id}` checks ownership in service; `DELETE /themes/{id}` checks ownership. Standard pattern — no divergence.
   - **For Phase 17, presets are NOT in DB.** They live in `presets.js` and are rendered in the same grid as custom themes. The page distinguishes them via the `kind` field on each theme object (`'preset'` vs `'custom'`).
