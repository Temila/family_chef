<objective>
Fix the TonalSpot variant's secondary/tertiary derivation so that changing the secondary or tertiary seed colors actually affects the generated CSS and visual preview.

Purpose: UAT Test 5 reports that dragging the secondary/tertiary color pickers produces no visual change. The root cause is that `deriveTonalSpotSchemes()` uses MCU's `themeFromSourceColor()` with `customColors` blend parameters — but MCU only stores those in `theme.customColors` (an independent array), never feeding them into `theme.schemes` or `theme.palettes`. As a result, `buildSchemeCss` reads primary-derived values for secondary/tertiary, ignoring the user's seed colors entirely. The other 8 variants are unaffected because they use `DynamicScheme` with explicit `secondaryPalette`/`tertiaryPalette` overrides.

Output: TonalSpot routed through the same `deriveDynamicSchemes` path as the other 8 variants (using `Variant.TONAL_SPOT`), plus a tertiary-visible element in `ThemePreview.jsx` so tertiary changes are perceptible. A new regression test verifies secondary/tertiary responsiveness.

Root cause evidence: `.planning/debug/secondary-tertiary-preview.md`.

**Phase 17 byte-stability note:** The header comment at theme-engine.js:1-8 states TonalSpot uses `themeFromSourceColor` to "保持 Phase 17 tokens.css 完全字节一致". MCU's `SchemeTonalSpot` (used internally by `themeFromSourceColor`) IS `DynamicScheme` with `Variant.TONAL_SPOT` — same primary/neutral/error palette derivation. Routing through `DynamicScheme` with `Variant.TONAL_SPOT` produces IDENTICAL primary/surface/elevation output. Only secondary/tertiary roles change (from primary-derived to seed-derived), which is the intended fix. The existing test assertions for `#056d37` (primary), `#81d997` (dark primary), and `#ffffff` (surface-container-lowest) will remain green because those roles are unaffected.
</objective>
