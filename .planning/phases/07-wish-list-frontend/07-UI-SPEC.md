## 3. Typography

Project already uses two weights (400 body, 600 emphasis) and 16px base font-size. Phase 7 inherits and adds no new fonts. **Constraint (locked):** no more than **4 distinct sizes** and **2 distinct weights** in any new wish UI surface.

| Role | Size | Weight | Line Height | Token chain | Usage |
|------|------|--------|-------------|-------------|-------|
| Meta / status badge | `12px` (0.75rem) | `400` | `1.4` | inherits `.badge` at `styles.css:112` | status badges, submitted time, submitter/chef names, secondary info |
| Body | `14px` (0.875rem) | `400` | `1.5` (`21px`) | inherits `body` rule at `styles.css:48` | note text, dish_picker items, form labels, card actions, table cell text |
| Modal title | `16px` (1rem) | `600` | `1.3` | inherits `.modal-header h3` (`styles.css:388`) | `WishFormModal`, `WishRejectModal`, `WishAdvanceModal` titles |
| Dish name / page title | `20px` (1.25rem) | `600` | `1.3` | `font-family: var(--font-display)` (Noto Serif SC) | WishCard top-row dish_name (D-11 large emphasis) AND page titles — **same role, same weight, same size** |

**Wish-specific emphasis rules:**

- `dish_name` (D-11) uses `font-display` + weight `600` at `20px` — locked. This is the only place where `font-display` is used.
- All other WishCard text uses body weight `400` (which covers badges, meta, and actions).
- Reference URL links (D-12) use body weight `400` + color `var(--accent)` — no underline (matches global `a` rule at `styles.css:49`).
- All `var(--text-muted)` text (timestamps, submitter_name when not primary) uses weight `400` for visual quietness.

Lock the 60-30-10 split with the existing design tokens. **The accent color is reserved for primary interactions only.**

| Role | Token | Value (light) | Value (dark) | Usage |
|------|-------|---------------|--------------|-------|
| Dominant (60%) — surfaces | `--bg-primary` / `--bg-secondary` | `#FFFFFF` / `#F8F9FA` | `#1E1E1E` / `#252525` | Page background, WishCard background |
| Secondary (30%) — containers | `--bg-card` / `--bg-elevated` | `#FFFFFF` / `#F0F1F3` | `#2A2A2A` / `#383838` | WishCard elevated surface, modal body, form input |
| Accent (10%) — primary interaction | `--accent` | `#1A73E8` | `#8AB4F8` | **Reserved for:** (1) primary CTAs ("新建愿望" header button, "提交愿望" modal submit), (2) active tab pill, (3) active nav item in Sidebar/BottomBar, (4) link color (`a` rule), (5) focused input border, (6) chef/admin context: the FAB-equivalent "认领" button uses primary blue. **NOT reserved for:** status badges (those use semantic colors), destructive actions (red), inline links inside card body (use `--accent` since they are links) |
| Destructive | `--danger` | `#D93025` | `#F28B82` | ConfirmModal `danger=true` button (撤销 confirmation), reject submit button; reserved exclusively for destructive actions per D-08 |

**Status badge color mapping (locked from D-16 + D-17):**

| Wish status (Chinese key, raw from backend) | Badge class | Token | Visual meaning |
|-------------------------------------------|-------------|-------|----------------|
| `待处理` | `badge-warn` | `--warn` (`#E8945A`) on `--warn-light` | "Attention needed" — pending claim |
| `准备中` | `badge-info` | `--info` (`#4A7A9A`) on `--info-light` | "In progress" — claimed, awaiting advance |
| `已上架` | `badge-success` | `--success` (`#34A853`) on `--success-light` | "Completed / positive" — linked to published dish |
| `已拒绝` | `badge-danger` | `--danger` (`#D93025`) on `--danger-light` | "Failed" — chef rejected with reason |
| `已撤销` | `badge-muted` | `--text-muted` on `--bg-elevated` | "Withdrawn" — submitter cancelled |

**Unread red dot (D-15):**

- Color: solid `#E74C3C` (a fixed red, identical to existing `.badge-count` background at `styles.css:121`)
- Size: `8px × 8px` (`width: 8px; height: 8px; border-radius: 50%`)
- Position: `position: absolute; top: 12px; right: 12px;` — adjacent to status badge top-right (badge is on top-right of top row; unread dot is 32px to the left of badge, also top-right)
- Accessible label: visually hidden text `<span class="sr-only">未读</span>` (new `.sr-only` utility; `position: absolute; clip: rect(0,0,0,0); width: 1px; height: 1px; overflow: hidden;`)
- Renders only when `wish.has_unread === true` (backend already enforces submitter-only exposure per Phase 6 D-B01)

**Reference link color (D-12):**

- Inherits `a { color: var(--accent); }` — no new token
- `target="_blank"` + `rel="noopener noreferrer"` (locked D-12 / Risk 7 mitigation)

**Destructive action accent (D-08):**

- Cancel confirmation: `btn-danger` (which is the existing pattern; reuse `ConfirmModal` with `danger={true}` — button uses inline `borderColor: var(--danger), color: var(--danger)` per existing `ConfirmModal.jsx:38-49`)
- Reject submit (inside `WishRejectModal`): red primary submit using `btn` class with inline `style={{ background: 'var(--danger)', color: '#fff' }}` — separate from ConfirmModal because this is the destructive execution, not a confirmation

**Dark mode behavior:** All status badge + accent tokens swap to dark variants automatically via `[data-theme="dark"]` rule at `styles.css:30-44`. The unread dot (`#E74C3C`) is **intentionally fixed** across light and dark themes — the high-saturation red remains perceptible against both backgrounds (verified ≥ 4.5:1 contrast in light mode, ≥ 3:1 in dark mode for the non-text UI component threshold per WCAG 2.1 SC 1.4.11).

## 5. Layout & Page-Level Structure

### 5.1 Page anatomy

All three wish pages (`UserWishesPage`, `ChefWishesPage`, `AdminWishesPage`) use the existing `PcLayout` shell (Sidebar + Outlet) and render:

```
┌─────────────────────────────────────────────┐
│ Header (sticky, 64px)                       │  ← existing .header
│   ← [back]  Page Title           [+ 新建]   │  ← user page only
├─────────────────────────────────────────────┤
│ Tab pills / filters (chef page only)        │  ← chef: 全部 / 待处理 / 我的认领
├─────────────────────────────────────────────┤
│ <WishCard /> × N                            │
│ <WishCard /> × N                            │  ← stack with 12px gap
│ <WishCard /> × N                            │
│ ...                                         │
├─────────────────────────────────────────────┤
│ BottomBar (mobile only, hidden ≥ 1024px)    │  ← existing .bottom-bar
│   [modified to include wish entry]          │
└─────────────────────────────────────────────┘
                                                  ↑ FAB on user page only
                                                  (bottom-right, 56px circle)
```

### 5.2 Card density (D-11)

- Mobile card viewport fits **3-4 cards** (320px-420px width × typical card height ~140px including padding and action row).
- Card height on mobile (default content): ~120-140px
  - Top row: 32px (dish_name + status badge side by side)
  - Meta row: 16px (submitted time + submitter/chef name when applicable)
  - Optional secondary lines: each ~20px (note, reason, related dish link)
  - Action row: 44px (button height ≥ 44px tap target)
- On desktop (≥ 1024px): cards stretch to `max-width: 720px` inside the side-padded `.pc-content-area`; centered with comfortable margin.

### 5.3 Page header heights

- User wish page header has **title left + "+ 新建愿望" right** action. Title height matches existing `.header-title` (line-height ~28px). Header total height: 64px (matches `--nav-height`).
- Chef / admin wish page header has **title only** (actions are inside tabs/filters).

### 5.4 Tab structure for `/chef/wishes` (D-03)

- Page-level pill tabs at top of content area, below header
- Three pills: **全部** / **待处理** / **我的认领**
- Visual: use existing `.filter-chips` + `.filter-chip` + `.filter-chip.active` styles (`styles.css:123-128`)
- URL state: `?tab=all|pending|mine` via `useSearchParams`
- Default tab: `all` (when no `?tab` param or invalid value, fall back to `all`)
- One tab visible at a time; clicking a tab swaps the wish list and updates URL

### 5.5 BottomBar + Sidebar additions (D-02)

**Sidebar (desktop, ≥ 1024px):** append one item per role array branch:
- `user` branch (currently 4 items) → append `{ icon: '💡', label: '我的愿望', path: '/my-wishes' }` AFTER `口味偏好` (sibling to `我的`)
- `chef` branch (currently 7 items) → append `{ icon: '💡', label: '愿望管理', path: '/chef/wishes' }` AFTER `口味偏好`
- `admin` branch (currently 9 items) → append `{ icon: '💡', label: '愿望总览', path: '/admin/wishes' }` (admin sidebar section)

**BottomBar (mobile, ≤ 1023px):** add one tab per role. **CRITICAL (Risk 4 mitigation):** Sidebar is hidden at ≤ 1023px (`.pc-sidebar { display: none !important; }` at `styles.css:380`), so BottomBar must include wish access or pages become undiscoverable.
- user tabs (3 currently): insert `{ id: 'user-wishes', icon: '💡', label: '愿望', path: '/my-wishes' }` after `点菜` and before `我的`. Final order: 首页 / 点菜 / 愿望 / 我的
- chef tabs (4 currently): insert `{ id: 'chef-wishes', icon: '💡', label: '愿望', path: '/chef/wishes' }` after `点菜`. Final order: 订单 / 点菜 / 愿望 / 首页 / 我的 (5 tabs total)
- admin tabs (4 currently): insert `{ id: 'admin-wishes', icon: '💡', label: '愿望', path: '/admin/wishes' }` after `菜品`. Final order: 后台 / 菜品 / 愿望 / 用户 / 退出 (5 tabs total)

**Active-state matching:** existing `isActive(path)` at `BottomBar.jsx:44-47` uses `startsWith(path + '/')` so `/admin/wishes` will not collide with `/admin`. Match exact path or `startsWith` per existing logic.

### 5.6 FAB on user page

- **Only** `UserWishesPage` renders the FAB (existing `.fab` style at `styles.css:191-192`)
- Icon: `+` (existing convention; or `💡` for thematic alignment, but `+` is more universal for "create new")
- Click → opens `WishFormModal` in `create` mode
- Position: `bottom: calc(var(--nav-height) + 16px); right: 24px;` (matches `.fab`)
- The header also has `+ 新建愿望` text button; both reach the same handler. (Belt-and-suspenders UX.)

**Label rule:** button labels include the noun (e.g., `编辑愿望` not `编辑`) so the action's intent is unambiguous on mobile tap surfaces.

**Admin caveat (Risk 10 mitigation):** Admin does NOT show submitter-only `[编辑] [撤销]` for wishes submitted by other users. Backend `wish_service.py` does not give admin an ownership override for edit/cancel. Only claim/advance/reject lifecycle actions are admin-overridable (D-04).

**Tap on WishCard body (Risk 3 mitigation, NOTIF-04):**

- Only meaningful for **submitter** cards where `has_unread === true`.
- Tapping the card body (not on a button or badge) triggers `api.getWish(id)` which:
  1. Clears the backend unread side-effect (only for submitter)
  2. Updates `has_unread: false` in local state for that card only
  3. Does NOT refetch the whole list
- For non-submitter viewers, clicking the card does nothing (no detail view is locked in scope).
- Cursor: `cursor: pointer` only on submitter cards with unread; `cursor: default` otherwise.
- Tap target accessible to keyboard: card has `role="button"` + `tabIndex={0}` + `onKeyDown` for Enter/Space when interactive.

### 6.2 WishFormModal (create + edit, D-05/D-06)

Reuses `.modal-overlay` + `.modal-content` shell. Width `480px` (matches existing).

## 7. Interaction Contracts

### 7.1 Tap targets & accessibility (Risk from RESEARCH.md:529-535)

- **All interactive elements ≥ 44px × 44px touch target.**
  - Action row buttons (`编辑愿望`, `撤销愿望`, `认领愿望`, `推进愿望`, `拒绝愿望`): `min-height: 44px; padding: 8px 16px;` — the 44px minimum is satisfied by `min-height` (not padding), keeping padding 4-aligned. **Note:** the canonical CSS rule for action buttons is in Section 6.1 (`.wish-card-actions .btn { padding: 8px 16px; }`) — this section's padding value must match.
  - Tab pills (chef/admin): already `.filter-chip` is shorter (~32px); explicitly set `min-height: 36px` for the wish-specific filter bar.
  - FAB: 56×56 (already).
  - Sidebar items: 240px width × ~44px tall (matches existing).
  - BottomBar tab items: existing flex layout automatically ≥ 44px tall because of `--nav-height: 64px` distributed.
- **Click event acceptable** but `onKeyDown` keyboard handler (`Enter` / `Space`) mirrors `onClick` for action buttons and tap-active cards.

### 7.2 Focus order & keyboard navigation

- On modal open: focus first field (`autoFocus` on `dish_name` for `WishFormModal`; on the `<textarea>` for `WishRejectModal`; on the search input for `WishAdvanceModal`).
- Tab order: header close ✕ → first field → second field → third field (or textarea only) → footer `[取消]` → footer primary submit.
- After modal close: focus returns to the opener element (button that opened the modal). Implementation: store `openerRef` on modal mount via React ref forwarding.
- Modal close on `Escape` (lock for accessibility — current implementation has none, RESEARCH.md:529-535). Document this in Section 7.5 modal accessibility.
- Modal body uses `role="dialog"` `aria-modal="true"` `aria-labelledby="<title-id>"`.

### 7.3 Hover / focus / active states

All inherit from existing tokens — no new states per status:

| State | Visual |
|-------|--------|
| Default | background `var(--bg-card)`, border `var(--border)` |
| Hover (desktop ≥ 1024px or `:hover` media-scoped) | border `var(--border-medium)`, box-shadow `var(--shadow-md)` (matches `.card:hover` at `styles.css:96`) |
| Focus (keyboard) | box-shadow `0 0 0 3px var(--accent-light)` (matches `.form-input:focus` at `styles.css:202`) |
| Active button | inherits `.btn-primary:hover { transform: translateY(-1px); filter: brightness(1.05); }` |
| Selected picker item (in `WishAdvanceModal`) | border `var(--accent)`, background `var(--accent-light)` (matches `.chef-select-item.active` at `styles.css:419`) |
| Read-only card (`已上架` / `已拒绝` / `已撤销`) | `opacity: 0.7`; no action row |

**Touch device rule:** disable hover lift on touch devices using `@media (hover: hover)` to avoid sticky hover on mobile.

### 7.4 Modal open/close flow

- **Open:** state change sets `actingModal: 'form' | 'reject' | 'cancel' | 'advance'`. Body overflow locks: `document.body.style.overflow = 'hidden'` for the duration.
- **Close** (any of the following): ESC key, ✕ click, overlay click, primary button success, cancel button.
- **Restore:** focus returns to opener; body overflow restored.
- **Page-level invariant:** only one modal may be open at a time (Risk: stacked overlays). Lock this with a single state discriminator.

### 7.5 Modal accessibility (NEW, not yet in codebase — RESEARCH.md:529-535)

Per W3C WAI modal dialog pattern (`https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/`), all four wish modals (`WishFormModal`, `WishRejectModal`, `WishAdvanceModal`, and reused `ConfirmModal` for cancel) MUST provide:

| Requirement | Implementation |
|-------------|----------------|
| `role="dialog"` | on `.modal-content` |
| `aria-modal="true"` | on `.modal-content` |
| `aria-labelledby` | on `.modal-content`, pointing to the `h3` title id |
| Initial focus | first form control or first focusable element |
| Contained tab nav | Focus trap inside modal (cycle tab from last to first) |
| ESC to close | `keydown` handler on `.modal-overlay` |
| Focus restoration | `useRef` on opener; restore via `openerRef.current.focus()` on close |
| `aria-describedby` | optional, pointing to inline error region when field errors exist |
| Icon-only ✕ close buttons | All four modals MUST add `aria-label="关闭{title}"` (e.g., `aria-label="关闭新建愿望窗口"`, `aria-label="关闭拒绝愿望窗口"`, `aria-label="关闭推进愿望窗口"`, `aria-label="关闭撤销确认"`) on the existing `.modal-close` button. |

Add a small `useFocusTrap.js` hook (or implement inline in each modal — three modals is acceptable for inline) to handle focus trap and ESC.

This is a **forward-fixing pattern** — the existing `ConfirmModal` does not have any of this today. Phase 7 applies the pattern to the three new modals and to `ConfirmModal` simultaneously, so the cancel flow is accessible too.

### 7.6 Polling & refresh (RESEARCH.md:519-528)

- **Chef/admin tabs (`/chef/wishes`, `/admin/wishes`)**: poll `GET /api/wishes?...` every **30s** while `document.visibilityState === 'visible'`. Reuse the `usePendingOrderCount` polling shape at `hooks/usePendingOrderCount.js:1-30` but with **stale-response guard**.
  - Monotonic request token (`requestSeqRef.current++` before each request; ignore response unless `seq === currentSeq`).
  - Cleanup: `clearInterval` on unmount or tab change; pause on `visibilitychange` to `hidden`.
  - Initial load: fire immediately on mount and tab change.
- **User page (`/my-wishes`)**: NO polling. Refresh on `visibilitychange` to `visible` + `focus` event. Background refetches show no spinner; foreground refetches show existing `<Loading />`.
- **After every mutation** (create/edit/cancel/claim/advance/reject): full refetch via `loadWishes({ background: true })`. Spinner suppressed; loading state is implicit via disabled action buttons.
- **Implementation note:** `loadWishes({ background: true })` is a wrapper around `api.getWishes()` that does NOT swap a `<Loading />` placeholder. Fresh action results are committed; older in-flight polling responses are dropped via the `requestSeqRef` guard.

### 7.7 Pagination & load-more (RESEARCH Risk 8)

The backend defaults to `page_size=20` and caps at 100. Lists must explicitly indicate when more items exist:

| Behavior | Implementation |
|----------|----------------|
| Initial fetch | `page=1, page_size=20` (locked) |
| Load-more control | When `items.length < total`, render a `<button class="wish-load-more">加载更多愿望</button>` below the card list |
| Load-more click | Increment `page` by 1, append to `items` array (do not reset) |
| Loading state | Button text becomes `加载中...` (existing `<Loading />` text) and is disabled during fetch |
| End-of-list state | When `items.length >= total` after final load, button is removed and replaced with `<div class="wish-end-of-list">没有更多愿望了</div>` |
| Failure | Toast `"加载更多失败，请稍后重试"` + button re-enabled |
| Tab change | Pagination resets to page 1; previously loaded items discarded |
| Polling behavior | Polling refreshes the **current loaded range only** (pages 1..N currently loaded). If `total` grew (new wish arrived), append a `加载更多愿望` button. Polling does not auto-load new pages. |
| All-tab on chef (`?tab=all`) | Most likely to need load-more; assume `total > 20` for any active family. |
| User page | Own wishes list typically ≤ 20; load-more is conditional. |
| Admin page | Same as chef — load-more likely active. |
